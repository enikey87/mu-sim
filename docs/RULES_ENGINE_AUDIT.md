## 1. Модель

Порт подхода Valve (L4D dynamic dialog) через kawaii-doom, с расширениями (по `DESIGN.md`): приоритеты речи, слоты, трассировка, расписание, факты со сроком.

```
Query(event, sender, target, facts) ──→ RuleSet.match / collect
     условия when: Criterion(key, op, value, scope, actor)
     resolver: каскад event → target → sender → world (`resolver`, blackboard.ts)
Rule → commit (once/cooldown/remember) → respond(ctx) → trigger[] (сразу или delay по дням)
```

Два режима выбора — архитектурно важная пара:
- **`match`** (ruleset.ts) — один победитель: «что ответить»;
- **`collect`** — все подходящие по убыванию специфичности, по одному на `slot`: «что предложить игроку» (BuildChoices).

## 2. Точная семантика выбора (прочитано, не предположено)

- Правила события отсортированы по убыванию специфичности при добавлении (`add`). Специфичность = `when.length + sender? + target? + bonus`, либо явный override (`specificityOf`).
- `match` идёт по списку; первое подошедшее правило фиксирует планку (`best`), всё ниже планки пропускается без бросков RNG. **Fallback есть**: если самое специфичное не прошло условия/шанс, победить может менее специфичное — планка ставится только по *прошедшему* правилу (цикл в `match`).
- Равные по специфичности — взвешенный shuffle без возврата, берётся первый (`weightedOrder`).
- `odds` бросается внутри `check` для каждого кандидата до победы — то есть бросок тратится и на проигравшие равные правила. Детерминизм сохраняется per-версия-кода, чего достаточно для replay плейтестов.
- **Приятная деталь**: с включённым tracer'ом правила ниже планки попадают в объяснение *без* броска шанса (комментарий «не тратя случайность» в `match`) — дебаг-режим не меняет RNG-поток. Осознанная защита воспроизводимости.
- `blocked`: priority floor → once → cooldown → odds; порядок важен — дешёвые проверки раньше броска.

## 3. Состояние и время

`RuleState` (types.ts) — plain JSON, живёт в сохранении игры: `once`, `cooldown` (по имени правила), `schedule` (отсортированное по дню), `groups`, `said`. Следствие: перерывы и «без повторов» переживают перезагрузку бесплатно.

- Часы движка — `{ turn, day }` извне (`now` в опциях): `turn` = число сообщений игрока, `day` — игровой день. Cooldown «в ходах» тикает только на сообщениях игрока — семантика осознанная, но невидимая в типах.
- Расписание: `schedule` — отложенные записи, откаты и события. Записи и откаты применяет `settle()` сразу при смене дня; события ждут `due()`, который зовёт `runDue`. События могут порождать события (`trigger.delay`) — мини-планировщик по дням.
- **Факты со сроком** (`forDays`): при записи захватывается *прежнее* значение ключа и ставится откат (ветка `forDays` в `applyOps`). Механизм простой; перекрытие двух записей одного ключа откатывает чужой факт — поэтому ключи со сроком разнесены по владельцам (закрытый угол 7.2).

## 4. Два контура чтения фактов

`fire` собирает `facts` один раз до `match`, а `respond` получает одновременно `ctx.facts` (снимок) и `ctx.get` (live-чтение досок через resolver). `commit` пишет `remember` **до** `respond`, поэтому снимок и live расходятся: условия проверялись по снимку, ответ читает свежее. Это не баг, а незадокументированная в API двойственность — автору правила нужно знать, каким из двух читать. Порядок сохраняется и после §7.1: откатывается уже записанное, а не откладывается запись.

## 5. Инструментарий (часть архитектуры, не приложение)

- **tracer** — объяснение каждого выбора (кандидаты, причины отказа) → дебаг-панель `?debug` и `rules:report`.
- **lintRules** (lint.ts) — статически ловит `shadowed` (подмножество условий + всегда доступно + специфичнее), `no-effect`, `bad-weight/odds`, а с `keyCheck` — `unknown-key` (ключ вне реестра `content/memkeys.ts`, #49; под префиксом — до элемента семейства, `content/factkeys.ts`, #103); гонится в тестах.
- **Lines** (lines.ts) — реплики «как в Hades»: when/prio/«сказано»/перерывы; стабильные id через djb2 по тексту.
- **Groups/Decks** (groups.ts, deck.ts) — shuffle без повторов, sequential, random, noRepeat; состояние сериализуемо.
- **Gated** (gated.ts) — требования на элемент любого пула, композиция `gate(...)`.

## 6. Сильные стороны (кратко)

Изоляция (ноль импортов из игры) · сериализуемое состояние · детерминизм под seeded RNG · объяснимость встроена, не прикручена · match/collect покрывают оба стиля выбора · время — first-class · 100% coverage gate в CI · линтер как часть модуля.

## 7. Острые углы

Каждый: механизм → последствие → вариант (✅ — прагматичный).

### 7.1. `once`/перерыв сгорали на пустом ответе — **закрыт** (откат commit + повторный match)
`commit` (с записью once/cooldown) выполняется **до** `respond`; `respond`, вернувший `false` («ничего не сделал»), теперь откатывает commit: `commit` возвращает функцию отката, `applyOps` пишет в него каждую запись и каждый отложенный элемент расписания (`applyOps`, `settle`), `fire` применяет журнал. Промолчавшее правило не тратит разовый шанс, не встаёт на перерыв, не оставляет памяти.
- После отката `fire` берёт **следующее** подходящее правило того же события (`skip` в `match`), а не отдаёт `null` сразу: иначе правило, условие которого навсегда ложно внутри `respond` (или пул реплик исчерпан), выигрывало бы каждый ход и заслоняло более общие. `null` — только когда промолчали все.
- Решение «говорить ли» **не** переносится за commit: `respond` читает память, которую записал его же `remember` (`Court_Step` в `content/rules/court.ts` — ступень суда берётся как «память уже сдвинута»), и перенос сломал бы правила, которые `false` не возвращают.
- Условие, которое не изменится (День выплаты прошёл), по-прежнему лучше в `when` — иначе правило зря выигрывает и откатывается на каждом ходе; движок уже не даёт ему заслонять остальных. Закреплено тестом «вечно молчащее правило не заслоняет…».
- Триггеры не тронуты: `trigger` без `ifResponded` у промолчавшего правила по-прежнему срабатывает; `ifResponded` для этого и существует.

### 7.3. Специфичность — неявная арифметика
`named(...)` считается за 1 условие независимо от содержимого (`named` в criteria.ts, «как в оригинале»); `bonus` — свободная ручка; `specificity` override не валидируется. Итог: относительный приоритет правил частично договорной; ошибка молча меняет выбор. Смягчается линтером (shadowed) и `rules:report`.
- ✅ Прагматичный: оставить как есть; при спорном приоритете — явный `specificity` с комментарием-причиной (конвенция).
- Альтернатива: валидация «override ≥ derived» в lint — ловит только одну из ошибок.

### 7.5. NaN молча гасит числовые условия
`Number(v ?? 0)` (`test` в criteria.ts): нечисловой факт → NaN → все `<`/`>=` ложны обе стороны — правило просто никогда не срабатывает, без сигнала.
- ✅ Прагматичный: в debug-режиме (tracer активен) `describeCriterion` помечает NaN-операнд — видно в панели, ноль стоимости в проде.
- Альтернатива: throw на NaN — превращает контентную опечатку в падение хода (см. TECH_AUDIT P1-1), хуже.
- **Отсутствующий факт читается как 0 — осознанно (#103).** Контент опирается на «ни разу» = 0 (`lte('asked.alik_death', 0)` — «не спрашивал», `lte('arc.alik_death', 3)`), и семантика «нет факта → ложь» сломала бы эти условия молча. Опечатку под префиксом (`since.daed`) до рантайма ловит `factkeys.ts`: семейство проверяется до элемента, а не до пространства имён; переименованный в `facts()` факт краснит `factkeys.test.ts` с обеих сторон. Единственное семейство, где «нет факта» ≠ 0, — `since.*` («тогда» без «было»): `memkeys.test.ts` требует у верхней границы `since.x` нижнюю (`gte(since.x, …)` или `ach.x`) в том же `when`.

### 7.6. `odds` в `collect` — мерцание вариантов при пересборке
`buildChoices` кэшируется в `S.choices`, но пересобирается на ход/idle/возврат; правило выбора с `odds` может то пройти, то нет между пересборками — вариант мигает. Частота низкая (пересборка = новый ход), последствие — косметика.
- ✅ Прагматичный: ничего не делать; зафиксировать как известное поведение.
- Альтернатива: запоминать исход броска в `S.rules` — состояние ради косметики.

### 7.7. Guard глубины цепочки — throw
`depth > 8` → `Error` (`fire`). Цикл в триггерах — контентная ошибка; падение обрывает ход, но игра не запирается: P1-1 закрыт (`finally` в `sendTurn`, `recoverTurn` в `answerJob`/`onIdle`).
- ✅ Прагматичный: оставить throw — падение видимое, цикл чинится по стеку.
- Альтернатива: `console.error` + обрыв цепочки — мягче, но цикл станет тихим.

### 7.8. Линтер shadowed сравнивает критерии текстом
Ключи условий — строки `describeCriterion` (`keys` в lint.ts): семантически равные `gte(x,5)`/`gt(x,4)` не распознаются. Ложных срабатываний нет, пропуски возможны — линтер консервативен по замыслу.
- ✅ Прагматичный: принять; ценность линтера в гарантии «нет false positive», а не в полноте.

### 7.9. Смена размера пула сбрасывает колоду
`st.n !== items.length` → состояние обнуляется (groups.ts): деплой с новым контентом молча сбрасывает «без повторов» у всех игроков. Последствие — возможный повтор реплики после обновления, не более.
- ✅ Прагматичный: принять (сброс безопасен по смыслу); при желании — мягкий merge: сохранить «виденные» индексы по пересечению текстов.

## 8. Что сознательно НЕ добавлять

- Плагины/middleware/шину событий — ~280 правил не оправдывают слой.
- Минутную гранулярность расписания — игровая единица времени = день.
- Версионирование `RuleState` внутри движка — покрывается бампом `SAVE_KEY` на уровне игры.
- Падение на неизвестное событие в `match` — пустой результат является валидным ответом («ничего не подошло»); опечатку в имени события ловит тип `GameEvent`.
