# Аудит системы правил (`src/engine/rules/`, main @ 1d830db, 2026-09-21; актуализировано @ 3692551, 2026-09-23; §7.1 закрыт @ 2077258 / доработан issue #78, 2026-09-24)

Отдельно от `ARCHITECTURE_AUDIT.md`: здесь — сам движок правил как изолированный модуль: модель, точная семантика выбора, состояние/время, инструментарий, острые углы. Метод: прочитаны все 9 модулей (~770 строк) и их тесты; покрытие 100/100/100/100 подтверждено прогоном `npm run test:rules`; номера строк сверены grep'ом на 3692551. Модуль не импортирует ничего из игры — `RuleSet<G>` generic, игра подставляется снаружи.

## 1. Модель

Порт подхода Valve (L4D dynamic dialog) через kawaii-doom, с расширениями (по `DESIGN.md`): приоритеты речи, слоты, трассировка, расписание, факты со сроком.

```
Query(event, sender, target, facts) ──→ RuleSet.match / collect
     условия when: Criterion(key, op, value, scope, actor)
     resolver: каскад event → target → sender → world (blackboard.ts:16)
Rule → commit (once/cooldown/remember) → respond(ctx) → trigger[] (сразу или delay по дням)
```

Два режима выбора — архитектурно важная пара:
- **`match`** (ruleset.ts:107) — один победитель: «что ответить»;
- **`collect`** (:132) — все подходящие по убыванию специфичности, по одному на `slot`: «что предложить игроку» (BuildChoices).

## 2. Точная семантика выбора (прочитано, не предположено)

- Правила события отсортированы по убыванию специфичности при добавлении (`add`, :54). Специфичность = `when.length + sender? + target? + bonus`, либо явный override (`specificityOf`, :10).
- `match` идёт по списку; первое подошедшее правило фиксирует планку (`best`), всё ниже планки пропускается без бросков RNG. **Fallback есть**: если самое специфичное не прошло условия/шанс, победить может менее специфичное — планка ставится только по *прошедшему* правилу (:113-124).
- Равные по специфичности — взвешенный shuffle без возврата, берётся первый (`weightedOrder`, :89).
- `odds` бросается внутри `check` (:65) для каждого кандидата до победы — то есть бросок тратится и на проигравшие равные правила. Детерминизм сохраняется per-версия-кода, чего достаточно для replay плейтестов.
- **Приятная деталь**: с включённым tracer'ом правила ниже планки попадают в объяснение *без* броска шанса («не тратя случайность», :114-119) — дебаг-режим не меняет RNG-поток. Осознанная защита воспроизводимости.
- `blocked` (:77): priority floor → once → cooldown → odds; порядок важен — дешёвые проверки раньше броска.

## 3. Состояние и время

`RuleState` (types.ts:147) — plain JSON, живёт в сохранении игры: `once`, `cooldown` (по имени правила), `schedule` (отсортированное по дню), `groups`, `said`. Следствие: перерывы и «без повторов» переживают перезагрузку бесплатно.

- Часы движка — `{ turn, day }` извне (`now` в опциях): `turn` = число сообщений игрока, `day` — игровой день. Cooldown «в ходах» тикает только на сообщениях игрока — семантика осознанная, но невидимая в типах.
- Расписание: `schedule` (:185) — отложенные записи, откаты и события. Записи и откаты применяет `settle()` (:191) сразу при смене дня; события ждут `due()` (:202), который зовёт `runDue`. События могут порождать события (`trigger.delay`) — мини-планировщик по дням.
- **Факты со сроком** (`forDays`): при записи захватывается *прежнее* значение ключа и ставится откат (:170-173). Механизм простой; перекрытие двух записей одного ключа откатывает чужой факт — поэтому ключи со сроком разнесены по владельцам (закрытый угол 7.2).

## 4. Два контура чтения фактов

`fire` собирает `facts` один раз до `match` (:245), а `respond` получает одновременно `ctx.facts` (снимок) и `ctx.get` (live-чтение досок через resolver). `commit` пишет `remember` **до** `respond` (:250), поэтому снимок и live расходятся: условия проверялись по снимку, ответ читает свежее. Это не баг, а незадокументированная в API двойственность — автору правила нужно знать, каким из двух читать. Порядок сохраняется и после §7.1: откатывается уже записанное, а не откладывается запись.

## 5. Инструментарий (часть архитектуры, не приложение)

- **tracer** — объяснение каждого выбора (кандидаты, причины отказа) → дебаг-панель `?debug` и `rules:report`.
- **lintRules** (lint.ts) — статически ловит `shadowed` (подмножество условий + всегда доступно + специфичнее), `no-effect`, `bad-weight/odds`, а с `keyCheck` — `unknown-key` (ключ вне реестра `content/memkeys.ts`, #49); гонится в тестах.
- **Lines** (lines.ts) — реплики «как в Hades»: when/prio/«сказано»/перерывы; стабильные id через djb2 по тексту.
- **Groups/Decks** (groups.ts, deck.ts) — shuffle без повторов, sequential, random, noRepeat; состояние сериализуемо.
- **Gated** (gated.ts) — требования на элемент любого пула, композиция `gate(...)`.

## 6. Сильные стороны (кратко)

Изоляция (ноль импортов из игры) · сериализуемое состояние · детерминизм под seeded RNG · объяснимость встроена, не прикручена · match/collect покрывают оба стиля выбора · время — first-class · 100% coverage gate в CI · линтер как часть модуля.

## 7. Острые углы

Каждый: механизм → последствие → вариант (✅ — прагматичный).

### 7.1. `once`/перерыв сгорали на пустом ответе — **закрыт** (откат commit + повторный match)
`commit` (с записью once/cooldown) выполняется **до** `respond` (:250); `respond`, вернувший `false` («ничего не сделал»), теперь откатывает commit: `commit` возвращает журнал откатов (:192), `applyOps` пишет в него каждую запись и каждый отложенный элемент расписания (:164, :184), `fire` применяет журнал (:253). Промолчавшее правило не тратит разовый шанс, не встаёт на перерыв, не оставляет памяти.
- **Что откатывает движок — и только это (issue #105):** отметку `once`, отметку перерыва (с #105 — возвращает прежнюю, истёкшую, а не стирает её), записи `remember` и их `forDays`. Записи, которые `respond` сделал сам (`game.S`, контекст, колоды, `seen`), движок не видит и не откатывает. Контракт: правило, которое может промолчать, решает это **до** первой своей записи (`Says_talk` сбрасывал контекст до проверки — исправлено; `sayFresh` двигал колоду впустую — возвращает её).
- **Проверка контракта — строгий режим** (`RuleSetOptions.silence`, у игры `strictSilence`): снимок `S` до `commit` сверяется со снимком после отката. Расхождение — `SilenceBreach`, и ход игрока её не глотает. Режим включён во всех тестах (`makeGame`) и в симуляции гейта покрытия (3 × 16 партий). В снимок не входит учёт выбора равных (`S.rules.groups`: его двигает сам `match`) и позиция генератора случайных чисел. В игре режим выключен: снимок на каждое правило стоит времени.
- После отката `fire` берёт **следующее** подходящее правило того же события (`skip` в `match`), а не отдаёт `null` сразу: иначе правило, условие которого навсегда ложно внутри `respond` (или пул реплик исчерпан), выигрывало бы каждый ход и заслоняло более общие. `null` — только когда промолчали все.
- Решение «говорить ли» **не** переносится за commit: `respond` читает память, которую записал его же `remember` (`content/rules/court.ts:38` — ступень суда берётся как «память уже сдвинута»), и перенос сломал бы правила, которые `false` не возвращают.
- Условие, которое не изменится (День выплаты прошёл), по-прежнему лучше в `when` — иначе правило зря выигрывает и откатывается на каждом ходе; движок уже не даёт ему заслонять остальных. Закреплено тестом «вечно молчащее правило не заслоняет…».
- Триггеры не тронуты: `trigger` без `ifResponded` у промолчавшего правила по-прежнему срабатывает; `ifResponded` для этого и существует.

### 7.3. Специфичность — неявная арифметика
`named(...)` считается за 1 условие независимо от содержимого (criteria.ts:20, «как в оригинале»); `bonus` — свободная ручка; `specificity` override не валидируется. Итог: относительный приоритет правил частично договорной; ошибка молча меняет выбор. Смягчается линтером (shadowed) и `rules:report`.
- ✅ Прагматичный: оставить как есть; при спорном приоритете — явный `specificity` с комментарием-причиной (конвенция).
- Альтернатива: валидация «override ≥ derived» в lint — ловит только одну из ошибок.

### 7.5. NaN молча гасит числовые условия
`Number(v ?? 0)` (criteria.ts:46): нечисловой факт → NaN → все `<`/`>=` ложны обе стороны — правило просто никогда не срабатывает, без сигнала.
- ✅ Прагматичный: в debug-режиме (tracer активен) `describeCriterion` помечает NaN-операнд — видно в панели, ноль стоимости в проде.
- Альтернатива: throw на NaN — превращает контентную опечатку в падение хода (см. TECH_AUDIT P1-1), хуже.

### 7.6. `odds` в `collect` — мерцание вариантов при пересборке
`buildChoices` кэшируется в `S.choices`, но пересобирается на ход/idle/возврат; правило выбора с `odds` может то пройти, то нет между пересборками — вариант мигает. Частота низкая (пересборка = новый ход), последствие — косметика.
- ✅ Прагматичный: ничего не делать; зафиксировать как известное поведение.
- Альтернатива: запоминать исход броска в `S.rules` — состояние ради косметики.

### 7.7. Guard глубины цепочки — throw
`depth > 8` → `Error` (:227). Цикл в триггерах — контентная ошибка; падение обрывает ход, но игра не запирается: P1-1 закрыт (`finally` в `sendTurn`, `recoverTurn` в `answerJob`/`onIdle`).
- ✅ Прагматичный: оставить throw — падение видимое, цикл чинится по стеку.
- Альтернатива: `console.error` + обрыв цепочки — мягче, но цикл станет тихим.

### 7.8. Линтер shadowed сравнивает критерии текстом
Ключи условий — строки `describeCriterion` (lint.ts:23–24): семантически равные `gte(x,5)`/`gt(x,4)` не распознаются. Ложных срабатываний нет, пропуски возможны — линтер консервативен по замыслу.
- ✅ Прагматичный: принять; ценность линтера в гарантии «нет false positive», а не в полноте.

### 7.9. Смена размера пула сбрасывает колоду
`st.n !== items.length` → состояние обнуляется (groups.ts:26): деплой с новым контентом молча сбрасывает «без повторов» у всех игроков. Последствие — возможный повтор реплики после обновления, не более.
- ✅ Прагматичный: принять (сброс безопасен по смыслу); при желании — мягкий merge: сохранить «виденные» индексы по пересечению текстов.

## 8. Что сознательно НЕ добавлять

- Плагины/middleware/шину событий — ~280 правил не оправдывают слой.
- Минутную гранулярность расписания — игровая единица времени = день.
- Версионирование `RuleState` внутри движка — покрывается бампом `SAVE_KEY` на уровне игры.
- Падение на неизвестное событие в `match` — пустой результат является валидным ответом («ничего не подошло»); опечатку в имени события ловит тип `GameEvent`.
