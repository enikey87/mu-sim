## 1. Слои и направление зависимостей

```
ui/ (компоненты) ─→ ui/view.ts (фасад GameUi + снимок View) ─→ engine/game, content (ACH, ARCS, ENDINGS, memkeys)
ui/App.tsx (корень) ─→ engine/game (Game → uiOf; живой Game — только DebugPanel)
engine/game.ts ─────→ content/* (20 импортов из 19 модулей: 18 рантайм + type-only rules/events)
content/rules/* ─────→ engine/game — ТОЛЬКО type-only (проверено: рантайм-цикла нет)
engine/rules/* ──────→ ничего из игры (изолированный модуль)
content (данные) ────→ engine/rules (критерии, gate) + фабрики с инъекцией (make(draw, getTier, rng))
```

С #77 граница UI держится механизмом, а не соглашением: компоненты получают фасад `GameUi` без `S` ни в типе, ни в объекте (обход кастом получает `undefined`), а импорты `src/ui/**` разбирает AST-страж `view.test.ts` (все виды импорта, подпапки). Исключения — `view.ts`, корень `App.tsx`, `DebugPanel.tsx`.

Фактическая топология — не «движок поверх контента», а **хаб-and-spoke с `Game` как хабом**: движок знает весь контент (18 рантайм-модулей в `game.ts`), контент правил получает `Game` через контекст ответа. Чистых границ две:

1. **`engine/rules/`** — genuinely isolated: не импортирует ничего из игры, покрытие 100% с CI-гейтом. Границу держит AST-страж `isolation.test.ts` (все виды импорта, подпапки; разрешены только `./*` и `../rng`) — не покрытие и не соглашение. Единственный модуль, который можно вытащить в пакет без единого изменения.
2. **Контент-данные** — словари/пулы параметризованы инъекцией (`make(draw, getTier, rng)` в `excuses.ts`), а не захардкожены на глобальное состояние.

Граница, которой **нет**: между «движком» и «игрой». `engine/game.ts` — это не движок жанра чат-симуляторов, а оркестратор именно этой игры: он знает про барана Бориса, День выплаты и бухгалтерию лжи.

## 2. Поток данных одного хода

```
ввод (кнопка/текст)
 → classifyUserInput (детерминированный классификатор, engine/input.ts)
 → push сообщения → touchMsgs(dirtyFrom) + emit (version++)
 → fire('PlayerSays' | 'PlayerMessage', facts)
     facts() — плоский снимок из S + mem + actors + вычислимые поля (ctx.topic, lateCount…)
     resolver: каскад event → target → sender → world (blackboard.ts)
     match: самое специфичное правило; равные — взвешенно
 → respond(ctx) → game.say/alikMsg → typingFor (паузы) → push
 → flushChorus (отложенные Mentioned) → advanceTurnDay → runDue (расписание) → StoryBeat → CheckEnding
 → buildChoices (collect по BuildChoices) → save → emit
```

UI подписан двумя каналами: `getVersion` (всё) и `getMsgsEpoch` + `getMsgsDirtyFrom` (лента — инкрементально). Это осознанная двухконтурная подписка: лента не пересобирается на смену статуса.

**Два контура времени** — ключевое архитектурное решение: игровые таймеры идут через `Clock` (ускоряемый `?fast`, ручной в тестах), UI-тосты/уведомления — через настенные часы `wallClock` (`window.setTimeout`, `?fast` не ускоряет). Разделение появилось после пойманного дефекта (`TECH_DEFECTS.md`: тост жил 78 мс под `?fast`); с #61 контуры разведены типами `GameTimer`/`WallTimer` — перепутанные часы не компилируются, сторож `@ts-expect-error` в `clock.test.ts`.

## 3. Состояние

| Контур | Что | Где живёт | Переживает reload |
|---|---|---|---|
| Игровое | `GameState`: день, долг, сообщения, сериалы, обещания | `S`, JSON blob в localStorage (`SAVE_KEY = alik-save-v4`) | да (сообщения — последние 150) |
| Память мира | `mem` (мир) + `actors` (доски персонажей) | внутри `S` | да |
| Состояние движка правил | once, cooldowns, расписание, «сказано» | `S.rules` (`RuleState`) | да |
| Анти-повторы | колоды (`S.bags`), хеши (`S.seen`), реплики (`S.rules.said`) | внутри `S` | да |
| Эфемерное UI | status, typing, toast, notif, moos, busy, feel, trace | `UiState` (`engine/ui-state.ts`, `game.ui`; #50), не в `S` | нет |
| Телефон | заряд (`S.battery` — в сохранении), «сел» (`dead`), прогресс зарядки (`charging`) | `Battery` (`engine/battery.ts`, `game.battery`; #66) | заряд — да, флаги — нет |

Сильное свойство: «без повторов» и паузы правил работают между сессиями, потому что состояние колод/правил — сериализуемое по замыслу (`GroupState`, `RuleState` — plain objects). Слабое: единый blob, shallow merge при загрузке, ручные латки (`rules.said ??= {}`) — см. TECH_AUDIT P3-2.

## 4. Паттерны и где они живут

| Паттерн | Где | Зачем здесь |
|---|---|---|
| Rule engine (Valve L4D: событие+факты → самое специфичное правило) | `engine/rules/ruleset.ts` | частный случай = новое правило, общий код не трогается |
| Blackboard (мир + доски персонажей, каскадное чтение) | `engine/rules/blackboard.ts` | «Борис болеет» читается из чужого условия |
| Реплики как в Hades (when/prio/«сказано») | `engine/rules/lines.ts` | контент с требованиями без if-else лесов |
| Колоды/группы (shuffle без повторов, sequential, noRepeat) | `engine/rules/groups.ts`, `engine/deck.ts` | анти-повтор между сессиями |
| Seeded RNG + ручные часы | `engine/rng.ts`, `engine/clock.ts` | воспроизводимые партии → playtest-бот с replay |
| Dispose-жизненный цикл | `GameDisposed`, `timerIds`, `sleepWaiters` в `game.ts` | async-ходы переживают unmount без утечек |
| Фасад/медиатор | сам `Game` | контент вызывает `game.say/line/fire`, не зная про UI |

## 5. Как архитектура обслуживает главное ограничение проекта

Проект — фабрика контента: сотни правил и тысячи вариантов реплик, которые должны быть взаимно согласованы (мир с памятью, ложь с поимкой, сериалы с финалами). Архитектура заточена именно под это:

- **Добавление реакции = одно правило** в `content/rules/` (пример в README). Специфичность вместо правки существующих веток — расширение без модификации (open/closed на практике, не на бумаге).
- **Контроль консистентности контента — инструментами, не глазами**: линтер правил (shadowed/no-effect), `rules:report` (что не срабатывает), playtest-бот с seed-replay, журналы огрехов в `docs/`.
- **Цена**: контент — программируемый TS, а не JSON/YAML. Автор контента = программист. Для этого проекта (один автор-программист) — правильный трейдофф; для «контент будут писать сценаристы» архитектура не подходит.

1. **`Game` как единственная точка интеграции (1735 строк на f197b4d).** Каждая новая механика растит хаб. Граница «игровое vs UI-состояние» с #50 структурная (`UiState`), но только для полей: поведение (`flash`, `notify`, `feelFor`) осталось в `Game`. ~~UI по-прежнему читает память движка напрямую — `S.mem[payday.chain]` (`Overlays.tsx`), `S.mem[payday.at]`/`[payday.sum]` (`Header.tsx`): строковых литералов больше нет (ключи из `memkeys`), но структура памяти UI видна.~~ **Чтение закрыто #64:** UI получает снимок из `ui/view.ts` (`viewOf(game)` + `feedMsgs(game)` для инкрементальной ленты); `S` и ключи `memkeys` видны только `view.ts` и `DebugPanel.tsx`. Сторож — `ui/view.test.ts`; с #77 он не ищет подстроки: компоненты получают фасад `GameUi` (`uiOf(game)`, без `S`), импорты разбираются AST компилятора TypeScript.
2. ~~**Плоский `mem: Facts` без реестра ключей.**~~ **Закрыто #49:** `content/memkeys.ts` — `MEM_KEYS`, `ACTOR_KEYS`, `EVENT_KEYS`; линтер отвергает неизвестный ключ (`lint.ts` kind `unknown-key`, прогон в `tools.test.ts`). Сырые литералы под семейством вне реестра ещё есть — `'topicMute.' + k` (`topicMuted` в `game.ts`), `` `wedding.${who}` `` (`weddingNoise` в `content/rules/world.ts`), а `mem.topicRun`/`mem.topicLast` (`says('topic')` в `content/rules/replies.ts`) — ключи реестра, но доступ свойством, не константой; до #103 префиксное правило их пропускало. **#103:** семейства проверяются до элемента (`content/factkeys.ts`: `arc.<id>` — по `ARCS`, `said.<claim>` — по `CLAIMS`, `met.<who>` — труппа + `EXTRAS`…), `EVENT_KEYS` сверены с `facts()` в обе стороны (`factkeys.test.ts`); `said.tomorrow`/`said.friday` — в реестре.
3. ~~**Нет view-model между UI и движком.**~~ **Закрыто #64:** `ui/view.ts` — единственный модуль UI, знающий устройство `S` и ключей памяти; компоненты получают плоский типизированный снимок (`viewOf`), лента — селектор `feedMsgs` поверх того же массива (инкрементальный канал `getMsgsEpoch`/`getMsgsDirtyFrom` не тронут). Контент-константы (`ACH`, `ARCS`, `ENDINGS`) превращаются в строки снимка внутри `view.ts`, в UI контент не импортируется вовсе. Исключение — `DebugPanel.tsx` (инструмент автора, читает `S.mem` напрямую); решаемо его включением в `uiFiles` стража, когда перестанет быть нужен. Редизайн или второй фронтенд реализует тот же снапшот, не наследуя внутренности `S`.
4. **«Движок» не переиспользуем.** `game.ts` статически импортирует 18 контент-модулей (рантайм); вторая игра на этом «движке» = форк, а не переиспользование. Если переиспользование когда-то понадобится — инверсия: регистрация контента снаружи (`new Game({ content })`), а не импорт внутри.
5. ~~**Двухконтурное время без типовой защиты.**~~ **Закрыто #61:** `Clock.setTimeout` возвращает `GameTimer`, настенные часы (`wallClock`, интерфейс `WallClock`) — `WallTimer`; бренды в `engine/clock.ts` делают перепутывание контуров ошибкой компиляции. Негативные контроли: `this.clock.clearTimeout(toastWall)` в `flash` не компилируется; снятие брендов валит typecheck на ставших лишними `@ts-expect-error` (`clock.test.ts`). Пузырь «Мууу» осознанно остался на игровых часах — эмбиент игрового темпа, а не UI для чтения; его снятие гоняется `runTimers` в тестах и плейтесте.
6. **Контент нарезан по механизмам, а не по пакам.** `arcs.ts` (41KB) держит все сериалы, `excuses.ts` (100KB) — все отмазки, `legends.ts` (45KB) — все легенды; контент одного персонажа размазан по 20 файлам (проверено grep'ом по `boris`: арки в `arcs.ts`, легенды в `legends.ts`, финалы в `finales.ts`, ложь в `lies.ts`, правила в `rules/world.ts`, реплики в `talk.ts`…). DLC-подобные паки (включаемые/отключаемые куски истории) режут поперёк этой оси: пак «Борис» = срез из ~8 механизм-файлов. Пока паков нет, это не баг, а трение при авторстве; блокером оно станет ровно в момент «отключить Самвела» — и чем больше контента накоплено к тому моменту, тем дороже перерез.

## 7. Что сознательно НЕ улучшать

- **Не выносить контент в JSON/данные** — убьёт главное свойство (§5): условия и хуки сцен — это код.
- **Не дробить `game.ts` «для красоты»** — сплит ради сплита даст дифф-шум без новых возможностей; выносить по одному модулю при реальном касании (кандидаты — в TECH_AUDIT P3-7).
- **Не делать из `engine/rules` фреймворк** (плагины, middleware, DI-контейнер) — ~300 правил не оправдывают ни одного из этих слоёв.
