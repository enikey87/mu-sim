# Отказы сети: классы асинхронных операций

> **Статус:** принято (1477), вариант 2 из разбора оператора 28.10.

Холодная загрузка — единственное место, где отказ сети виден игроку до того, как игра появилась.
Но и после старта каждая новая асинхронная операция (import(), fetch(), регистрация воркера, отдача
прогресса в облако) решает один и тот же вопрос: что увидит игрок, если сеть не ответит. Документ
фиксирует **классы отказа** и правило, по которому новую операцию нельзя добавить молча.

## Классы

| Класс | Что обещает игроку | Где эталон в коде | Чем проверено |
|---|---|---|---|
| `boot` | Отказ виден и его можно пережить: индикатор не вечный, есть повтор и понятный финальный текст | Инлайн-сторож в `index.html` (ошибка загрузчика + тайм-аут 12 с + guard перезагрузки), повтор пакета в `src/intro/retry.ts`, шелл `src/intro/shell.ts` | `tests/e2e/net-failures.spec.ts`, `src/tools/boot-shell.test.ts`, `src/intro/retry.test.ts` |
| `fallback` | Отказ не виден как ошибка: операция подменяется заведомо рабочей веткой, игра идёт дальше в урезанном виде | `src/platform/index.ts` (`bootPlatform`: чанк адаптера или SDK упали — остаётся веб), `src/sw/register.ts` (воркера нет — обычная загрузка) | `src/platform/platform.test.ts`, `tests/e2e/sw.spec.ts` |
| `fire-and-forget` | Отказ не меняет ничего: событие аналитики, отметка, замер уходят в консоль и в очередь не копятся | `src/analytics/metrics.ts` (`safe()`: тег не грузится — игра не ждёт), `docs/design/analytics.md` | `src/analytics/*.test.ts` |

Класс — свойство операции, а не места вызова: один и тот же `import()` может быть `boot` (пакет
приложения) и `fallback` (чанк адаптера витрины), это разные операции с разными обещаниями.

## Правила

1. **Новая асинхронная операция объявляет класс в PR.** В описании PR — строка «класс отказа: boot /
   fallback / fire-and-forget» и видимое поведение при отказе. Нет класса — ревью красное
   (ведущий фабрики, `.claude/skills/factory-lead/`).
2. **`boot` не оставляет вечного индикатора.** У операции есть предел ожидания и финальное состояние:
   текст, называющий причину и действие («проверьте сеть и обновите страницу»), и, где возможно,
   кнопка повтора. Инлайн-сторож холодной загрузки — не фреймворк: только текст и одна перезагрузка.
3. **`fallback` называет запасную ветку в одном месте** — там, где операция объявлена, а не в каждом
   вызывающем. Игроку отказ не показывают: показывают работу урезанного пути.
4. **`fire-and-forget` не блокирует игру и не показывает ошибку.** Его отказ — строка в консоли или
   телеметрии; офлайн-очереди для аналитики нет по дизайну (`docs/design/analytics.md`).
5. **Смена класса — решение, а не уборка.** Перенести операцию из `fallback` в `boot` (или наоборот)
   значит изменить обещание игроку; это называется в PR явно.

## Почему повтор идёт перезагрузкой

`import()` того же адреса после сетевого отказа браузер не повторяет: module map помнит неудачу и отдаёт
ту же ошибку, не делая запроса. Поэтому повтор главного пакета (`src/intro/retry.ts`) — перезагрузка
страницы с номером попытки в `sessionStorage`: новый документ делает честный `import()`, а игрок видит
строку «дозваниваемся… N из 3». Наивный «повторить тот же `import()`» в e2e выглядит как три попытки,
но сеть видит одну — `tests/e2e/net-failures.spec.ts` считает документы, а не строки лога.

Второй способ — адрес чанка из манифеста сборки с `?attempt=N` — отвергнут: вычисленный путь `import()`
запрещён сторожем `src/test/imports.test.ts`, и обходить его ради повтора нельзя.

## Границы

- Service worker не трогаем: его стратегии (cache-first для ассетов, network-first для навигации)
  проверены отдельно, и `boot`-сторож не должен подменять его решения (`tests/e2e/sw.spec.ts`).
- Сторож холодной загрузки целиком инлайновый: внешний файл не доедет ровно в том сценарии, который
  он лечит. Бюджет инлайна — 4 кБ вместе с индикатором (`src/tools/boot-shell.test.ts`).
- Авто-перезагрузка без guard в `sessionStorage` запрещена: при мёртвой сети это цикл.
