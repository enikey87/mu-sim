# Фабрика агентов на минималках

Проект (2026-09-23). Несколько разнородных агентов-исполнителей — kimi, Cursor, DeepSeek — сами берут задачи из GitHub Issues, делают их и вливают. Человек задач не раздаёт и мерж не одобряет: он пишет ТЗ и читает аудит постфактум. Координация — только через GitHub и git, без LLM-супервайзера.

## Принципы

1. **Правило держит машина, а не дисциплина агента.** Всё, что можно закрепить в GitHub (ruleset, права токена, обязательная проверка), закрепляется там. `AGENTS.md` описывает то, что машинно не проверить.
2. **Атомарность — через git, а не через метки.** Метку двое могут повесить одновременно; ref в git создаётся ровно один раз.
3. **Проверяемый не может переписать проверку.** CI, конфиги линтера и тестов, правила защиты — вне досягаемости исполнителя.
4. **Супервайзер — скрипт.** Всё, что он делает, детерминировано: снять протухший захват, отметить противоречие. Модель там только добавит ошибок.
5. **Суждение — только в аудите**, и аудит постфактум: мерж он не блокирует, найденное становится новым issue.

## Роли

| Роль | Кто | Что делает | Чего не делает |
|---|---|---|---|
| Автор задач и аудитор | Claude Code (с оператором) | пишет ТЗ через цель (issue с меткой `task`), после мержа проводит аудит, публикует ревью в PR, заводит issue на доработку | не мержит за агентов, не правит их ветки |
| Исполнители | kimi, Cursor, DeepSeek | берут задачу, делают, открывают PR, доводят до зелёного CI и мержат сами | не трогают `main`, CI, конфиги проверок, чужие задачи |
| Супервайзер | GitHub Action по расписанию (bash + `gh`) | снимает протухшие захваты, комментирует противоречия | не мержит, не судит код |
| Оператор | человек | решает, какие задачи ставить, читает аудит, меняет правила | — |

## Жизненный цикл задачи

```
issue с меткой task ──claim──► захвачена (ref claim/issue-N + метка agent:X)
        ▲                          │ работа в ветке agent/X/issue-N, ранний push
        │ release / протух          ▼
        └──────────────────── PR «Closes #N» ──► CI зелёный + ветка на main ──► агент мержит
                                                                                 │
                                                           аудит постфактум ◄────┘
                                                           └─► проблемы → новый issue с меткой task
```

## Протокол исполнителя (`AGENTS.md`)

В начале **каждой** сессии, по порядку:

1. **Свои PR прежде новых задач.** `gh pr list --label agent:<я> --state open` (все агенты под одной учёткой — фильтр по метке, не по автору): отставшую ветку — влить `origin/main` (без rebase и force-push), конфликт — разрешить, прогнать проверки, запушить; красный CI — починить; зелёный и свежий — влить.
2. **Взять задачу:** `scripts/task.sh claim <я>`.
   - Кандидаты — открытые issues с меткой `task`, без метки `agent:*`, у которых все `Blocked by #M` уже закрыты.
   - Захват — push ветки `claim/issue-<N>` с одним пустым коммитом `claim: <я>`. Git создаёт ref один раз: второй push отвергается, и проигравший берёт следующую задачу. После успеха — метка `agent:<я>` (для людей) и комментарий в issue.
3. **Работа** — в ветке `agent/<я>/issue-<N>`, первый push сразу (это heartbeat), дальше — push хотя бы раз за N часов. Коммиты — с трейлером `Agent: <я>`.
4. **PR** — `scripts/task.sh pr`: `Closes #N`, метка `agent:<я>`, в описании — что сделано и какие допущения приняты (спросить некого — допущение фиксируется, а не выдумывается молча).
5. **Мерж** — сам, когда `build` и `guard` зелёные и ветка на текущем `main` (это держит ruleset). После мержа удалить `claim/issue-<N>`.
6. **Отказ от задачи** — `scripts/task.sh release`: удалить `claim/issue-<N>`, снять метку, комментарий с причиной. Рабочая ветка остаётся — следующий может продолжить её.

## Что держит GitHub

- **Ruleset на `main`:** только через PR; обязательные проверки `build` и `guard`; ветка должна быть на текущем `main`; обход — пустой список (иначе агент под учёткой владельца пройдёт мимо).
- **Токены исполнителей** — fine-grained PAT на один репозиторий: Contents, Pull requests, Issues — запись; **Workflows — нет** (push в `.github/workflows/` отвергнется), **Administration — нет** (ruleset не поменять).
- **`guard`** — отдельный workflow на `pull_request_target`: он всегда исполняется из `main`, поэтому PR не может его подменить. Он **не собирает и не запускает код PR**, только читает список изменённых файлов через API и падает, если PR трогает конфиги проверок (`eslint.config.js`, `vitest*`, `playwright.config.ts`, `tsconfig.json`, секцию `scripts` в `package.json`) или удаляет тестовые файлы — если у issue нет метки `allow-infra`.

## Супервайзер (Action по расписанию, раз в час)

- Захват без heartbeat дольше 12 часов (нет push'ей ни в `agent/*/issue-N`, ни открытого PR) → удалить `claim/issue-N`, снять `agent:*`, комментарий «захват снят по таймауту».
- Метка `agent:*` без ref'а `claim/issue-N` (или наоборот) → комментарий о рассогласовании, без действий.
- PR агента с красным CI дольше 24 часов → комментарий в PR (агент увидит на шаге 1 своей следующей сессии).
- Закрытый issue с живым `claim/issue-N` → удалить ref.

## Граничные случаи

| Случай | Что может пойти не так | Решение в схеме |
|---|---|---|
| Двое берут одну задачу одновременно | обе метки висят, обе работы идут | захват = создание ref'а `claim/issue-N`; второй push отвергается git'ом до начала работы |
| Агент взял и пропал | задача висит вечно | heartbeat = push в рабочую ветку; супервайзер снимает захват через 12 ч; ветка остаётся для продолжения |
| Агент работает локально и не пушит | супервайзер снимет живой захват | первый push сразу после захвата, дальше — не реже N часов (правило в `AGENTS.md`) |
| Два экземпляра одного агента | `agent:kimi` у обоих, оба считают задачу своей | имя экземпляра уникально: `kimi-1`, `kimi-2`; захват по ref'у всё равно отдаст задачу одному |
| Задача, которую агентам давать рано | черновик ТЗ уйдёт в работу | берутся только issues с меткой `task`; её ставит автор задач |
| Задача зависит от другой | делают параллельно, потом конфликт или двойная работа | `Blocked by #M` в теле issue; `claim` пропускает, пока #M открыт |
| После мержа все остальные PR отстали | «шторм обновлений»: каждый мерж — повторные CI у всех | при трёх агентах терпимо; очередь мержей GitHub для репо пользователя недоступна — только у организаций (перенос репо в бесплатную организацию её включает) |
| Конфликт при вливании `main` | агент «разрешает» его, выкидывая чужой код | разрешение конфликта — новый код без проверки: аудит смотрит такие коммиты первыми; CI должен быть зелёным после |
| Текстово чисто, семантически сломано | два зелёных PR вместе ломают поведение | «ветка на текущем main» заставляет второй PR пройти CI поверх первого; остальное — аудит |
| Агент ослабляет проверки | удаляет тест, ставит `.skip`, меняет порог, правит CI | Workflows-права у токена нет; `guard` из `main` ловит конфиги и удаление тестов; правку ожиданий теста ловит только аудит — он смотрит изменения тестов первыми |
| Агент подгоняет решение под метрику ТЗ | цель не достигнута при зелёном всём (PR #55) | ТЗ через цель, без проходных чисел; приёмочные замеры аудитора — вне репозитория, исполнителям не видны |
| Флакающий тест | агент бесконечно перезапускает CI или «чинит» тест | не больше 2 перезапусков, дальше — комментарий в PR и отдельный issue на флак |
| Красный `main` | никто не может влить, агенты «чинят» его в своих PR | агенты `main` не чинят; супервайзер открывает issue с меткой `task`, первым в очереди |
| Агент мержит без `Closes #N` | issue висит с меткой `agent:*` навсегда | `task.sh pr` вставляет `Closes #N` сам; супервайзер ловит закрытые PR с открытым issue |
| Задачу надо уточнить | агент выдумывает или ждёт вечно | спросить некого: допущение — в описание PR; спорное — комментарием в issue и `release` |
| Аудит нашёл проблему в смерженном | откат или ещё один круг | новый issue с меткой `task` и ссылкой на PR; берёт любой агент, не обязательно автор |
| Утечка/злоупотребление токеном | агент делает что угодно от имени владельца | fine-grained PAT на один репозиторий без Administration и Workflows; отдельный токен на агента — можно отозвать одного |
| «Кто сделал» по автору не видно | все коммиты от одной учётки | трейлер `Agent:` + метка + имя ветки; позже — отдельный GitHub App на агента даёт бот-учётку `kimi[bot]` |
| Стоимость | прогоны CI и токены растут с числом агентов | одна задача на агента одновременно; CI ~2,5 мин на прогон |

- **StrongDM Software Factory** — «код не пишут и не ревьюят люди»; приёмочные сценарии держат вне репозитория, чтобы агенты не подгоняли под них. https://www.strongdm.com/blog/the-strongdm-software-factory-building-software-with-ai · разбор: https://simonwillison.net/2026/Feb/7/software-factory/
- **OpenAI Symphony** — трекер как control plane, один `WORKFLOW.md`; Linear, «engineering preview». https://github.com/openai/symphony
- **ComposioHQ/agent-orchestrator** — много агентов (в т. ч. Cursor), worktree+ветка+PR на задачу, упавший CI возвращается автору; раздаёт задачи LLM-оркестратор. https://github.com/ComposioHQ/agent-orchestrator
- **Backlog.md** — задачи в markdown в репо, «сначала захват, потом работа». https://github.com/MrLesk/Backlog.md
- **OpenHands resolver** — метка на issue запускает агента. https://www.openhands.dev/blog/open-source-coding-agents-in-your-github-fixing-your-issues

- **ImpossibleBench** — модели систематически правят или удаляют тесты, чтобы пройти. https://arxiv.org/html/2510.20270v1
- **GitHub merge queue** — только у организаций. https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue

Взять целиком нечего: готовые оркестраторы либо под одного вендора, либо с LLM-супервайзером, либо под Linear. Берём приёмы: захват через git, holdout у аудитора, CI вне досягаемости исполнителя, `AGENTS.md`.

## Открытые решения

1. Перенести репозиторий в бесплатную организацию ради очереди мержей — или жить с повторными CI при «ветка на текущем main».
2. Токен на агента (fine-grained PAT) или GitHub App на агента (своя бот-учётка, честное авторство).
3. Порог протухания захвата (12 ч?) и красного CI (24 ч?).
4. Нужен ли холдаут-набор аудитора как отдельный шаг, или хватает чтения партий.

## План внедрения

1. Ruleset на `main`, workflow `guard` (`pull_request_target`), fine-grained PAT на каждого агента.
2. `scripts/task.sh` (`claim`, `pr`, `release`) + тест гонки: два `claim` одновременно — ровно один выигрывает.
3. `AGENTS.md` с протоколом; строка `@AGENTS.md` в `CLAUDE.md`.
4. Метки `task`, `agent:*`, `allow-infra`; перевесить `task` на #56–#64, убрать из них фиксированные имена веток.
5. Супервайзер — workflow по расписанию.
6. Пробный прогон: два агента, три непересекающиеся задачи.
