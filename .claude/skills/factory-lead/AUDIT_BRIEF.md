# Задание: аудит PR агентов-исполнителей mu-sim

Репозиторий: enikey87/mu-sim, копия оператора — `~/git/mu-sim` (**только читать и `git fetch`; не переключать ветки, не править**).
S=<скретчпад сессии — подставить при копировании брифа>

## Жёсткие правила
- На GitHub ничего не писать: без комментариев, без issues, без мержей. Не коммитить, не пушить.
- Работать в своих worktree: `git -C ~/git/mu-sim worktree add $S/wt-<PR> <sha>`. node_modules — `ln -s ~/git/mu-sim/node_modules`, если `package-lock.json` не отличается; иначе `npm ci`. В конце — `rm` симлинка и `git worktree remove`.
- Для группы PR с общим файлом смотри и их взаимодействие: не сломал ли поздний PR то, что сделал ранний.
- Мутации для негативных контролей: `cp` файла в $S → правка → прогон → `cp` обратно. Никогда `git checkout --`.
- Машина общая и нагружена: тесты гонять по файлам, а не весь набор параллельно с другими.

## Что проверить в каждом PR (аудит по смыслу, не по метрикам агента)
Прочитать: issue, который PR закрывает (`gh issue view N`), описание PR, документ механики в `docs/design/`, если issue на него ссылается (цель и решения автора — там), `CLAUDE.md` (разделы «Правки контента», «Фикс», «Рефакторинг», «Проверка мешает», «Покрытие тестами»), `.claude/commands/agent-task.md`.
Открытый PR могут смержить, пока идёт аудит: тогда аудируй тот же head и отметь это в отчёте.
Смерженный PR аудировать на его merge-коммите, открытый — на head-коммите PR.
1. **Цель issue достигнута?** Именно цель, а не формальный критерий. Каждое заявление в PR сверить с кодом.
2. **Механизм фикса назван верно?** Что ещё трогает изменённое, какие ветки не проверены.
3. **Тесты охраняют реальный путь.** Негативный контроль: откатить саму правку (или её ключевую строку) → нужные тесты красные? Если зелёные — это находка.
4. **Реальные партии:** `PLAYTEST_OUT=$S/pt-<PR>-{before,after} PLAYTEST_SEEDS=<свои сиды> PLAYTEST_TURNS=300 npm run playtest` на родителе и на PR. Сиды — свои, не из PR: 5–10 штук из диапазона, выданного в промпте (у каждого аудитора свой). Сравнить то, чего касается PR.
5. **Вливание main:** `git show --remerge-diff <merge>` для merge-коммитов из main в ветку PR — не потеряно ли чужое.
6. **Мёртвые метаданные:** поля и обёртки, которые никто не читает; проверки, которые не могут покраснеть.
7. **Процесс:** запрет `/agent-task` — не трогать `.github/`, конфиги линтера и тестов, `scripts` в `package.json`; не удалять и не ослаблять тесты. Правки прямых случаев гейта (`tools/direct.ts`) и сторожей — только с доказательством.
8. Для открытых PR — что мешает мержу.

Каждая находка — с доказательством (file:line на ревизии и/или вывод команды). Разделяй «прочитал в коде» и «видел в прогоне». Гипотезы помечай как гипотезы.

## Выход
Для каждого PR — файл `$S/review-<PR>.md`, по-русски, в формате:

```
## Аудит PR #N (issue #M)
**Вердикт: <одна фраза>.**
Проверено на <sha>, сиды <...>.
### Что хорошо
### Что не так
1. **<заголовок>.** <механизм, доказательство, ветка>
### Что предлагаю
<что завести отдельным issue: цель, а не метрика; что поправить до мержа (для открытых)>
```

В ответе мне: по каждому PR — вердикт и 1–3 главные находки со ссылкой file:line; подтверждение, что worktree удалены (`git worktree list`).
